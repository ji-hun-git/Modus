# Modus architecture and privacy audit — 28 October 2026

Modus currently implements a local, owner-reviewed health-record timeline with source provenance, preserved disagreements and historical availability filters. Its bounded assistant answers from a smaller measurement projection. This is a useful integrity architecture; it is not yet an authenticated, encrypted service for real personal records, and neither technical novelty nor SOTA quality has been established.

This audit read current source, the supplied kit's original README, `02_skill/building-ai-agents/SKILL.md`, failure catalogue, identity/observability references and spec/eval/threat/stack templates. It also read the project's README, build brief, progress, goals, adoption/spec/threat documents and the owner's pasted novelty review. No credential file, held-out data or provider API was accessed. Existing release evidence remains historical evidence; this audit does not overwrite it. Production privacy changes below are a proposed contract, not implemented features.

## What the code actually does

`backend/modus_entry/app.py` exposes one local profile. An upload becomes a persisted draft and original. Local parsing, local OCR, or two bounded Spark passes propose recorded fields; a person explicitly selects and edits fields before a transaction saves them. `record_history.py` preserves the original proposal separately from reviewed values and detects a changed retry rather than applying a different second commit. `record_history_view.py` applies event and availability bounds before returning facts or originals. The model has no record-write, SQL, shell, arbitrary URL or messaging tool.

The generic store supports eight kinds: measurement, encounter, recorded diagnosis, procedure, prescription, vaccination, imaging text and recorded text (`record_history_models.py:11`). These are typed containers for recorded statements, not eight clinically validated reasoning capabilities. Normalization preserves original strings and only applies explicit rules. The assistant still obtains `observations` from the legacy projection; `MetricArgs` in `modus_entry/tools.py:68` permits only HbA1c, eGFR and LDL. A medicine or vaccination shown in Timeline is not therefore available to the assistant. “Ask about your whole history” would overstate the present contract.

One file can appropriately become one Home module containing its reviewed facts, dates, review state and source action. That presentation must retain one stable source identity rather than suggesting that visual cards are independent medical conclusions. Derived cross-file summaries should identify every contributing source and the captured scope.

## Time and provenance contract

| Time | Current meaning | Required wording and behavior |
|---|---|---|
| `occurred_on` / legacy `date` | Date printed for the measurement/event; partial dates retain their original string and do not become invented days. | “When it happened,” with precision and unknowns. |
| `reported_at_raw` / legacy `reported_at` | Source-reported issue time where supplied; generic CSV preserves the raw value. It is not uniformly extracted or normalized across every document path. | “When the source issued this version,” retaining evidence and uncertainty. |
| `ingested_at` | Server receipt when the original becomes a draft (`record_store.py:183`). | “Added to this device,” not clinically known or accepted. |
| `reviewed_at` / `committed_at` | Server transaction time after explicit review. | “Accepted into Modus.” A future authenticated actor must replace a constant label. |
| `available_at` with `review_commit` | Admission to the reviewed Modus record, currently equal to commit time (`record_history.py:97,108`). | “Available in Modus.” This is not when the person or institution first knew the result. Seed data uses separately declared synthetic availability. |
| `known_at` | A query cutoff over the application's admitted records. | “Records available in Modus by …”. Historical filtering uses today's deterministic code, not a replay of a past model's internal state or the person's knowledge. |

Do not overload these fields to claim real-world awareness. If future imports include a documented person-received time, retain it as a distinct source assertion with its own basis. FHIR already separates clinically relevant `effective[x]` from version availability `issued`; system-versioned database history is established prior art. [FHIR Observation](https://www.hl7.org/fhir/observation.html), [SQL Server temporal tables](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables?view=sql-server-ver17).

## Privacy without removing the service

The proposed order is: **unlocked encrypted local vault → local parse/OCR → source module and review → explicit redacted cloud preview when needed → bounded extraction or query → human-reviewed save**. The original remains encrypted locally; a redacted derivative has its own hash and a local mapping back to original coordinates. Store minimal transfer receipts, not raw provider conversations by default. Keep local history, search and export useful when cloud permission is denied. Never imply that masking creates anonymity or that cloud permission certifies a provider's policy.

OS-backed key protection is a practical implementation component, not complete product security. Windows DPAPI normally ties decryption to the user's logon credentials; its machine-wide mode has different access semantics and should not be selected casually for a personal vault. Apple Keychain is intended for small secrets such as encryption keys, not as the entire record store. [Microsoft DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata), [Apple key management](https://developer.apple.com/library/archive/documentation/Security/Conceptual/cryptoservices/KeyManagementAPIs/KeyManagementAPIs.html).

Meta states that ZDR requires separate organization-level enablement and is not standard usage. This audit did not inspect the owner's account policy or establish ZDR coverage. Do not advertise zero retention from use of the API alone. [Meta ZDR help](https://dev.meta.ai/help/policies-and-privacy/zero-data-retention).

## Novelty and evidence claims

The pasted review's claims that personal records have never been built this way, that no named competitor has these properties, and that a chatbot cannot retain history are not established by this code audit or by absence of public product documentation. “Novel in combination” is a research hypothesis until a systematic prior-art comparison supports it. The defensible present contribution is an explicit, tested combination of reviewed admission, source-preserving disagreements, historical scope and bounded factual answers in an owner-facing service. Do not claim a new temporal database, clinical validation or SOTA extraction from this implementation.

The current live evidence proves a narrow authored workflow ran. It does not establish performance across medical documents. The retained 16 requests include two HTTP errors; the reported estimate covers usage returned by 14 successful completions and is not an invoice. Test counts measure software regression coverage, not medical accuracy. Wider product goals remain in the goal registry; the contest boundary remains factual record integrity.

## Freshness check and concrete dependency fix

The original kit script ran with `--no-models`; the saved review run used a minimal child environment containing only system/path/temp variables. `research/kit-freshness-20261028-review.json` retains 31 registry/spec attempts, of which 21 responded and 10 timed out. Unused SDK changes are not recommendations. The bounded OSV audit checked actual locked httpx 0.28.1, FastAPI 0.162.0, pypdf 6.21.2 and Pillow 12.3.0. The first three returned no entries; Pillow returned 41 advisories requiring applicability review, not 41 proven Modus exploits.

Upstream confirmed [GHSA-g4qv-2jxx-769h](https://github.com/python-pillow/Pillow/security/advisories/GHSA-g4qv-2jxx-769h) affects Pillow 11.0.0–12.3.0 and is patched in 13.0.0. The main runtime now specifies `Pillow>=13,<14` and locks 13.0.0; the existing optional OCR lock already used 13.0.0. [Release notes](https://pillow.readthedocs.io/en/stable/releasenotes/13.0.0.html) were reviewed. The two dependency inventories now include Pillow and its installed MIT-CMU license notice. They also repair a pre-existing pypdfium2 5.14.0 inventory omission, preserving its 18 declared license files from the installed Windows wheel. Other dependency versions were preserved. The general inventory generator currently matches license basenames rather than all `License-File` declarations; that generator needs a separate correction before regenerating these inventories.

Validation: `uv --system-certs pip install --python .venv/Scripts/python.exe Pillow==13.0.0`; `uv pip check` reported 28 compatible packages; targeted extraction/smoke tests passed **96/96**. New coverage checks valid PNG orientation and rejection of a less-than-1-KiB repeated-EXIF fixture before any model request. The initial expectation that malformed metadata would be accepted failed; the patched decoder correctly rejects it, and the final test asserts that behavior. This is a bounded regression, not an exploit stress test or complete parser security proof. The follow-up OSV query for Pillow 13.0.0 returned no entries. No production Python adapter changes, provider requests, held-out evaluation or changes to prior public candidates were made. The parent owns the next full release gate.
